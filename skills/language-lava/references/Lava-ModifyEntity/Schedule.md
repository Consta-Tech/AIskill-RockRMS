# Creating a Schedule via `{% modifyschedule id:'0' %}`

Notes on what is (and isn't) required when creating a `Schedule` entity through the `{% modifyschedule %}` Lava command, with the `id` parameter set to `'0'` to signal "create new".

## TL;DR

You can create a `Schedule` with `{% modifyschedule id:'0' %}` by populating `Name` + `iCalendarContent` and leaving everything else blank — including `WeeklyDayOfWeek` and `WeeklyTimeOfDay`. The save will succeed, and the Schedule will be fully functional. Rock parses `iCalendarContent` and derives occurrences, check-in windows, effective dates, and friendly text from the parsed iCal event.

## What is required

**Database level** (per the `CREATE TABLE [dbo].[Schedule]` script in `database-structure-tables.md`), only these columns are non-nullable on `Schedule`:

- `Id` — identity
- `Guid` — auto-generated by `{% modifyentity %}`
- `IsActive` — `bit`, has DB default `0`; the C# property defaults to `true`
- `Order` — `int`, has DB default `0`
- `AutoInactivateWhenComplete` — `bit`, has DB default `0`

**Entity level** (`Schedule.cs`), only `IsActive` carries a `[Required]` data-annotation, and it has a C# default of `true`:

```csharp
[Required]
[DataMember( IsRequired = true )]
[Previewable]
public bool IsActive { get; set; } = true;
```

**No other property** — including `Name`, `iCalendarContent`, `WeeklyDayOfWeek`, and `WeeklyTimeOfDay` — has `[Required]`. The XML doc above `Name` says "This property is required", but no attribute backs that claim, and the column is `nvarchar(50) NULL` in SQL.

## iCalendarContent vs. Weekly fields

`iCalendarContent` and the `WeeklyDayOfWeek` / `WeeklyTimeOfDay` pair are **alternative scheduling mechanisms**, not parallel requirements:

- `iCalendarContent` is the primary, full-fidelity source — an RFC 5545 string with `VEVENT`, `RRULE`, etc. Rock parses it via `InetCalendarHelper.CreateCalendarEvent(...)` (see `Schedule.Logic.cs:526`) and derives runtime behavior from the parsed event.
- `WeeklyDayOfWeek` + `WeeklyTimeOfDay` is a simple-case fallback. Code paths that consult these fields do so only when `GetICalEvent()` returns null. From `Schedule.Logic.cs:775-776`:

  ```csharp
  // if there is no CalEvent, it might be scheduled using WeeklyDayOfWeek
  return WeeklyDayOfWeek.HasValue;
  ```

  The same fallback pattern repeats at lines 815 and 973.

Rock does **not** auto-derive one from the other. If you populate `iCalendarContent` only, the Weekly* fields stay `NULL`. If you populate Weekly* only, `iCalendarContent` stays empty. Both are valid creation paths; `iCalendarContent` is the recommended one.

## SaveHook behavior

The entire `PreSave()` in `Schedule.SaveHook.cs` is:

```csharp
protected override void PreSave()
{
    this.Entity.EnsureEffectiveStartEndDates();

    if ( this.Entity.Name.IsNullOrWhiteSpace() )
    {
        this.Entity.Description = this.Entity.ToFriendlyScheduleText( true );
    }

    base.PreSave();
}
```

Notably, **there is no validation that rejects a save when `iCalendarContent` is null or empty.** The hook only does two things:

1. Recomputes `EffectiveStartDate` / `EffectiveEndDate` (see next section).
2. If `Name` is blank, auto-fills `Description` from `ToFriendlyScheduleText()`.

## EnsureEffectiveStartEndDates behavior

From `Schedule.Logic.cs:380-398`:

```csharp
internal bool EnsureEffectiveStartEndDates()
{
    var calEvent = GetICalEvent();
    if ( calEvent == null )
    {
        EffectiveEndDate = null;
        EffectiveStartDate = null;
        return false;
    }
    // ... derives EffectiveStartDate / EffectiveEndDate from calEvent
}
```

When `iCalendarContent` is null/blank, `GetICalEvent()` returns `null`, the method gracefully nulls both effective-date columns, and returns `false`. **No throw, no rejection.**

## Recommended creation pattern

```lava
{% comment %}
    Obtain a valid iCalendarContent string by either:
    1. Creating a Schedule once through Rock's Schedule Builder UI, then reading
       [Schedule].[iCalendarContent] from SQL, or
    2. Copying the iCalendarContent of an existing Schedule with the same shape.
{% endcomment %}

{% capture var_iCalendarContent %}{{ existing_or_generated_ical_string }}{% endcapture %}

{% modifyschedule id:'0' return:'modify_NewSchedule' %}
    [[ Name ]]My Weekly Schedule[[ endName ]]
    [[ iCalendarContent ]]{{ var_iCalendarContent }}[[ endiCalendarContent ]]
    [[ IsActive ]]true[[ endIsActive ]]
{% endmodifyschedule %}

{% if modify_NewSchedule.Success == true %}
    Created Schedule successfully.
{% else %}
    Error creating Schedule: {{ modify_NewSchedule.ErrorMessage }}
{% endif %}
```

Notes on this pattern:

- `id:'0'` is the create-new idiom for `{% modifyentity %}`.
- `return:'modify_NewSchedule'` follows the lava-conventions house rule — never rely on the default `ModifyResult`.
- `[[ IsActive ]]true[[ endIsActive ]]` is technically redundant (the C# default is `true`), but stating it explicitly makes the intent obvious to a future reader.
- For the full return shape and additional `{% modifyentity %}` semantics, see `skills/language-lava/references/Lava-Language.md` > "Modify Entity Command".

## Updating an existing Schedule

When updating an existing Schedule via `{% modifyschedule id:'<existing>' %}`, write `iCalendarContent` as the only property in the block. Do **not** include `EffectiveStartDate` / `EffectiveEndDate` alongside it.

### The silent no-op (Tested May 2026)

Combining all three properties in one `{% modifyschedule %}` UPDATE block:

```lava
{%- comment -%} silently no-ops the iCalendarContent write {%- endcomment -%}
{% modifyschedule id:'{{ var_ScheduleId }}' securityenabled:'false' return:'modify_Schedule' %}
    [[ property name:'iCalendarContent' ]]{{ var_iCal }}[[ endproperty ]]
    [[ property name:'EffectiveStartDate' ]]{{ var_FirstOccurrenceStart }}[[ endproperty ]]
    [[ property name:'EffectiveEndDate' ]]{{ var_LastOccurrenceEnd }}[[ endproperty ]]
{% endmodifyschedule %}
```

was observed to:

- Return `modify_Schedule.Success == true` (no `ErrorMessage`).
- Leave `[Schedule].[Id]` unchanged (this was a real UPDATE, not a silent CREATE).
- **Leave `[Schedule].[iCalendarContent]` unchanged in the DB** — the iCal write itself silently no-op'd despite Success.

Same shape as the `{% modifygroup %}` / `IsArchived` quirk in [`../Lava-Language.md`](../Lava-Language.md) > "modifygroup and Archive Properties".

### The working pattern

Isolate `iCalendarContent`:

```lava
{% modifyschedule id:'{{ var_ScheduleId }}' securityenabled:'false' return:'modify_Schedule' %}
    [[ property name:'iCalendarContent' ]]{{ var_iCal }}[[ endproperty ]]
{% endmodifyschedule %}
```

`EffectiveStartDate` / `EffectiveEndDate` are redundant on every Schedule save — see [SaveHook behavior](#savehook-behavior) and [EnsureEffectiveStartEndDates behavior](#ensureeffectivestartenddates-behavior) above.

### What's untested

- Whether the same shape affects CREATE (`id:'0'`) blocks. Empirically, CREATE has been observed to succeed even with all three properties present, but defensive callers may still prefer to isolate `iCalendarContent` for symmetry.
- Whether other property combinations with `iCalendarContent` (e.g., `Name`, `IsActive`) trigger the same shape on UPDATE.

When in doubt, isolate the suspect property and verify via direct DB read.

## Caveats

- A Schedule with **neither** `iCalendarContent` **nor** `WeeklyDayOfWeek` populated is functionally inert — it has no times. The save will still succeed, but every downstream consumer (occurrence enumeration, check-in, friendly text) will return empty/false until you populate one.
- If a *specific* Block or report reads `WeeklyDayOfWeek` directly rather than going through `GetICalEvent()`, it will show blank for iCal-only Schedules. Most core Rock paths use the iCal route, but check the consumer if you see unexpected blank UI.
- The `iCalendarContent` getter (`Schedule.Logic.cs:45-57`) coerces `null` to empty string when reading. Downstream Lava that does `{{ obj_Schedule.iCalendarContent }}` will see `""`, never `null`.
- These findings are pinned to commit `b9083f1282ff63537bd3e1219936892577bcc888`. Re-verify against current Rock source before relying on them in a different Rock version.
